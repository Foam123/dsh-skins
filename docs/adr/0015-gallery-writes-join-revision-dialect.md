# 图库写并入修订号写方言：delete 前置条件、悬空预览自愈与清空图库单次提交

---
status: accepted
date: 2026-10-20
---

## 背景

GLOSSARY「修订号」词条曾登记缺口：图库上传/删除不携带前置条件。代码实证（v1.5.11 走查 + 独立子代理调查交叉确认）：`applyOperations` 在串行队列内校验 `baseRevision`（store.js:442-447），`uploadAsset`/`deleteAsset` 无条件直写——同一份 `state.json` 上并存两套写方言。最尖锐的边：

- `deleteAsset`（store.js:587-613）**读改写配置拥有的数据**（清除引用它的壁纸字段）却不走配置写的前置条件；删除确认对话框只列**已持久化**引用，预览层引用不可见。
- 悬空预览死循环：预览层引用被删资产的 flush 撞 `MISSING_ASSET` → 整批 400 → 全部预览保脏（config-client.js:276-284）→ 此后**任何**字段的自动保存都被这一个毒丸阻塞（PATCH 整批校验、整批拒绝），直到用户手工重选。单/批量上传成功即自动应用壁纸值（panel.js:384/370），悬空预览正好在主通路出口待命，无需双标签即可触发。
- 清空图库 = N 次串行 DELETE、N 次落盘、非原子、首错即停（panel.js:240-271）。
- 测试盲区：store 测试与 client 测试互相 mock 对方，`delete → 冲突 → 重试 → MISSING_ASSET` 序列无人覆盖。
- 服务端单进程串行队列保证状态文件不撕裂——缺口的实质是**表达力与客户端不可自愈状态**，不是服务端一致性。

## Decision

- **操作词汇并入 PATCH**（Q6-α）：`operations` 的 op 扩为 `set | delete | deleteAsset | clearLibrary`。`deleteAsset` 携带资产 id；`clearLibrary` 对应 GLOSSARY 既有领域词「清空图库」，服务端展开、天然绕开 1–64 条上限对百图图库的钳制。前置条件、冲突重试、结构化 issues、单次提交全部复用 PATCH 既有机器；清空图库 = 一个 PATCH、一次 commit、一次修订号 bump，字段回退与资产删除原子成立。op 词汇表具名 + 白名单测试钉住（ADR-0014 风格：interface 变宽必须动 seam 构造点）。
- **deleteAsset 存在性严格 fail-closed**（Q10-a）：目标不存在 → 具名 issue `ASSET_NOT_FOUND`、整批原子拒绝；客户端在冲突 refetch 后发现资产已不在快照 → 静默无操作。`clearLibrary` 不带 id，天然幂等（空图库 = 目标已达成，成功返回）。
- **同批次序语义**：全部操作先对批前状态校验、再按数组序应用（现行字段批语义的自然延伸）；同批 `set X` 后跟 `deleteAsset X` 会先设后被引用清除回退，终态一致、无悬空。
- **上传豁免前置条件**（Q3-b）：上传是纯追加、不改写字段，不可能覆盖他人数据；`requireNormal` 已挡恢复/只读态。这是设计裁决，不是缺口——为上传加前置条件只在 20MB 传输前多一次握手，换取空的冲突保护。
- **悬空预览自愈**（Q2-a/Q7）：`INVALID_CONFIG` 响应体携带结构化 `issues: [{opIndex, skinId, key, code}]`（code 复用 `MISSING_ASSET / BAD_ASSET / BAD_VALUE / …` 既有词汇）。客户端对**悬空类**（`MISSING_ASSET`、`BAD_ASSET`）：摘除该预览、字段回退默认、面板点名「壁纸已失效，已回退」；对**其他类**：预览保持脏态 + 具名报错（不悄悄丢用户输入）。批次服务端仍整批原子，不改 ADR-0001 语义。删除确认对话框同时列出持久化引用与预览层引用。
- **混版宽容**（Q4-a）：旧式 `DELETE /library/{id}` 路由保留为兼容适配器（升级瞬间旧标签页持有旧 bundle），无前置条件 = 今日无条件语义；不设删除期限，下个大版本再议。
- **修订号保持单一计数器**（Q5-a）：一切状态提交（字段写、图库删除、上传落库）都 +1。拆双计数器会让快照失去单一版本身份——重新引入第二种方言，且 delete 本身跨两域。
- **两项捎带**（Q1b）：① 上传成功**本地合并**（响应已含 `{asset, revision}`，追加不改引用表，免整份 refetch，批量往返 2N→N+1）；② 上传自动应用的那条预览**立即 flush**（跳过 400ms 防抖；普通编辑仍走合并窗）。
- **PATCH 响应**： gallery 操作在场时携带 `affectedSkins`（面板反馈「哪些字段已回退」复用现有形状）。

## Considered Options

- **复合操作「上传即设为壁纸」单往返（(c)）——搁置、不锁死**：用户感知为零差异（现状本就零额外点击、预览层本地实时投影）；无竞争路径省一跳不可感知，冲突路径要么 409 整体重试（重传 20MB 字节），要么服务端降级为「blob 照收、set 打回」——而降级编舞恰是本裁决本身。将来若做，走 amendment，且需修正「上传豁免」裁决（复合写不再是纯追加）。
- **DELETE 路由加 `x-base-revision` header + 另设批量清空端点（(β)）——被否**：协议表面积 +2，前置条件/重试/issues 机器在两条路由各写一份，等于把第二写方言制度化。
- **deleteAsset 服务端幂等（missing = 成功）——被否**：把「删错了东西」与「已被删过」变成同一应答，静默吞掉 stale-UI 之外的误删；双标签删除竞态由前置条件 refetch 路径自然消化。
- **无前置条件 = 409 逼刷新——被否**：把升级变成打断。
- **客户端解析 400 文本猜字段——被否**：文本耦合，反向重蹈 rgba 解析缝的覆辙。

## Consequences

- 图库删除成为显式配置写；第二写方言消失（DELETE 路由缩为薄兼容适配器），前置条件/重试/逐项裁决机器集中于一处（locality）。
- 上传→设壁纸的用户感知零变化；批量上传往返 2N→N+1；悬空预览从「永久毒丸」变为「点名 + 自动回退」。
- 验收围栏（Q8 五件）：① delete 操作前置条件冲突 → 409 → refetch 重试成功（单测 + 真 store 集成）；② 悬空预览全链路：删图 → flush 撞 `MISSING_ASSET` → 只摘该预览 → 下次 flush 其余字段成功（真 store + 真 config-client 跨缝集成，补上两侧互相 mock 的盲区）；③ 清空图库单次提交：混入非法 id → 整批拒绝零落盘；④ 混版宽容：无前置条件的旧式 DELETE 路由在新 Host 上行为不变；⑤ 两项捎带各自测试（本地合并不再整份 refetch；上传自动应用的预览立即 flush）。
- GLOSSARY 已随裁决更新：「修订号」改写为快照级乐观锁（删除也是写、上传纯追加），新增「悬空预览」词条。
- 行为变化（协议 + 失败自愈 UX），独立正式版本发版，沿仓库发版纪律（`docs/developers.md`「发版」节）。
- 与 ADR-0001/0003 不冲突：批次原子与自动保存语义不变，变化只在失败的可表达性。
